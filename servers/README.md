# Porkbun Pricing Server (REST + MCP)

Node server that exposes Porkbun TLD pricing and recommendation features from the JSON generated by the core fetcher.

Primary mode is REST (good fit for Docker/public hosting), with optional MCP stdio mode still available.

## What this solves
- Ask for cheapest TLDs by renewal/registration/transfer cost
- Ask for details on a specific TLD
- Ask for recommended TLDs for a domain idea with price-aware ranking

## Data dependency
This server reads:
- `../../core/porkbun-domains-filtered.json` (resolved from `servers/src`)

Generate or refresh that file from the core project first:

```bash
cd ../core
npm install
npm start
```

## Install and run (REST)

```bash
cd ../servers
npm install
npm start
```

Default address:
- `http://0.0.0.0:3000`

Useful endpoints:
- `GET /health`
- `GET /api/tlds/cheapest?maxResults=10&sortBy=renewal`
- `GET /api/tlds/com`
- `GET /api/recommendations?idea=ai+startup&maxResults=5`
- `POST /api/recommendations`
- `GET /openapi.json`

## Optional MCP stdio mode

If you still want native MCP stdio for desktop clients:

```bash
npm run start:mcp
```

## REST API Contract

1. `GET /api/tlds/cheapest`
- Query:
  - `maxResults` (optional, 1-100)
  - `maxRenewal` (optional, positive number)
  - `sortBy` (optional: `renewal` | `registration` | `transfer`)

2. `GET /api/tlds/:tld`
- Path:
  - `tld` (required, like `com`, `io`, `ai`)

3. `GET /api/recommendations`
4. `POST /api/recommendations`
- Body/query:
  - `idea` (required)
  - `maxResults` (optional, default 5)
  - `maxRenewal` (optional)

## MCP Tools (if using stdio)

1. `get_cheapest_tlds`
- Inputs:
  - `maxResults` (optional, default 10)
  - `maxRenewal` (optional)
  - `sortBy` (optional: `renewal` | `registration` | `transfer`)

2. `get_tld_details`
- Inputs:
  - `tld` (required, like `com`, `.io`, `ai`)

3. `recommend_tlds_for_idea`
- Inputs:
  - `idea` (required)
  - `maxResults` (optional, default 5)
  - `maxRenewal` (optional)

4. `get_data_source_info`
- Inputs: none
- Shows loaded file path and total TLD count

## Docker deployment

Build image:

```bash
docker build -t porkbun-pricing-rest ./servers
```

Run container (mount core output JSON):

```bash
docker run --rm -p 3000:3000 \
  -e PORKBUN_DATA_PATH=/data/porkbun-domains-filtered.json \
  -v /workspaces/porkbun-domain-tld-pricing-fetcher/core:/data:ro \
  porkbun-pricing-rest
```

This image now runs with `pm2-runtime` by default.

Why this helps in Docker:
- process supervision and automatic restart policy inside container
- structured logs from PM2
- clean path to run multiple processes if ever needed

Practical caveat:
- If you run under Kubernetes/ECS with robust restart policies, plain Node as PID 1 is also valid.
- PM2 in container is most useful when you want PM2 features (logs/restarts/ecosystem config) consistently across VM + Docker.

## Docker Compose with scheduled JSON updates

If you want refreshes fully encapsulated in containers, use the root compose stack:

- `pricing-updater` (cron container) refreshes Porkbun JSON on a schedule
- `pricing-api` serves REST API from the same shared data volume

Start stack from repo root:

```bash
cd ..
docker compose up -d --build
```

Default schedule is every 6 hours (`0 */6 * * *`).

Change schedule by editing `CRON_SCHEDULE` in `docker-compose.yml`, for example:
- every hour: `0 * * * *`
- every 12 hours: `0 */12 * * *`

Inspect logs:

```bash
docker compose logs -f pricing-updater
docker compose logs -f pricing-api
```

Stop stack:

```bash
docker compose down
```

## PM2 (process manager)

Install PM2 globally if needed:

```bash
npm install -g pm2
```

Start all services from this folder:

```bash
cd ../servers
npm run pm2:start
```

Useful PM2 commands:

```bash
npm run pm2:logs
npm run pm2:restart
npm run pm2:stop
npm run pm2:delete
npm run pm2:save
pm2 status
```

Ecosystem file:
- `ecosystem.config.cjs`

Important note:
- `porkbun-rest-api` is the recommended PM2 target for hosting.
- `porkbun-mcp-stdio` can run under PM2, but stdio MCP is usually meant to be spawned by MCP clients directly. For public/remote deployments, use REST as primary.

## Do we need FastAPI first?
Short answer: no.

Because this project is already Node, a REST service in Node is enough for hosted use and Docker.

FastAPI is only needed if you specifically want a Python stack.

You only need an HTTP API/gateway if you want:
- remote/shared access over network
- web-only clients that cannot spawn local stdio processes
- auth, rate limiting, and tenant isolation for public use

## OpenWebUI compatibility
Recommended hosted approach:
- Use this REST server directly.
- Point OpenWebUI tool integration at your API base URL.
- Use `/openapi.json` for schema-driven integration where supported.

If your OpenWebUI deployment requires strict MCP transport, keep `npm run start:mcp` as fallback.

## Future GitHub OAuth (public deployment)
Best practice:
- Keep OAuth out of the MCP tool logic itself.
- Put GitHub OAuth in an external gateway layer in front of REST API.
- Gateway handles login/session/token verification, then forwards allowed requests.

Suggested phased rollout:
1. Local/hosted REST (current)
2. Add GitHub OAuth app + session store
3. Add authz/rate limits/observability
4. Optionally add MCP gateway/bridge for strict MCP-only clients
